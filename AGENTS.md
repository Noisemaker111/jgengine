# JGengine repository governance

This file holds how this repo builds, tests and lands, and what "done" means here; nothing that applies to every repo (those rules live in `~/.config/opencode/AGENTS.md`). [README.md](README.md) owns project facts: packages, layering, commands and publishing. Do not restate them here or in skills.

## Project purpose

JGengine is measured by the time from an idea to a deep playable game; friction an agent hits while building a game is an engine bug to fix. JGengine is built through distinct playable games in `games/`. Reviewing a game exists to improve the shared framework, so one fix reaches every game. Trace a game symptom to its real cause, the engine contract, its adoption or the game's own rules, before fixing it: an obstructed HUD does not justify game-local CSS, and apparent sinking does not justify a guessed offset.

The engine is small general systems that combine into any game; it never ships a game's feature as one closed thing. A supply drop is not an engine feature. It is a game combining a schedule that spawns things at a pace from a start time, a rarity table, an access rule tied to that rarity, a loot pool per rarity, and a motion and landing animation, so the game's tick says `spawnSupplyDrop(x, y, "purple")` in a few lines it wrote. Breeding, taming, boss fights, police and every other named feature break down the same way. The test for each piece: a game that wants only part of it (simple dog breeding, a shooter's ammo crate) uses that part and throws nothing away. Much of today's code was built for one game and is being taken apart, so never copy a feature's shape because it exists; build the systems it should have been made of.

## Writing

Write short everywhere a human reads, one idea per line, in plain words and the tone of a calm coworker.

- Chat reply: what you did, what is open, the links.
- PR body: written by `lane:close` from its `-m` lines (one per change, in plain words; `Fixed:` / `Added:` / `Removed:` / `Migrate:` pick the changelog heading), plus `-m "Closes #N"` and, for a bugfix, `-m "Root cause: ..."`. It adds the exported API the diff changed, the engine seam and the Bends itself.
- Issue: the problem in one sentence plus acceptance criteria.
- Leave out plan recaps, rejected options, file walkthroughs, restated output and closing summaries. Keep facts, guesses and suggestions apart.
- A decision for the user is one concrete question with the options named.

Code comments default to none. Exported public API keeps tight JSDoc (it generates `api.md` and `capabilities.md`). Inside a function, comment only a non-obvious why.

## Product invariants

- **World content is authored in the editor.** Placement, terrain, paths, zones, foliage and assets live in `editor.scene.json`, authored through the editor GUI or RPC/CLI and consumed at runtime through shared primitives. Changing visible world content is an editor task first; if the editor cannot express it, file a `[FEATURE]` issue before any code fallback. Never hardcode coordinate arrays a scene can own (`jgengine-editor`, `jgengine-world`).
- **Reusable capability goes upstream first.** Name the shared owner before editing a game. Adopt what exists, or fix its package; anything another game could need goes in `packages/*` as a narrow, configurable seam with a real adopter.
- **Build for every game, not the one in front of you.** A JGengine game can be anything, so every engine feature is separate parts a game can switch off, swap or retune, and it is named for the general idea: a summoned encounter, not an obelisk boss; a growth stage list, not ARK's baby/juvenile/adolescent. Fixed lists (stages, tiers, body plans, damage types, camera views, difficulty levels) are data the game supplies, and a game's numbers live in its config, never in engine defaults, names or docs. No presets, archetypes, default-genre shapes or one fixed API per genre or vehicle class; probe games are not templates. A folder no in-repo game imports is deleted, not kept general; git keeps it, and it comes back with the game that needs it.
- **Build from the parts.** Before writing a `create*` factory or a feature folder, name the parts it combines ([README.md](README.md#the-parts)). A bounded value, a tier list, a stage list, a pace over time, a spawn location, a weighted pick, a condition, a modifier stack, an inherited value or a path over time uses that part's home, never its own copy; a part that lacks something gets it added there, with a test. A feature folder holds only what is left after the parts: its own rules and names.
- **Simulations are separate effects.** Every physical effect (tyre slip, weight transfer, drift, drag, wind, thrust lapse, ground effect, autorotation, buoyancy and the rest) is its own named term with its own toggle and parameters; never a realism slider, so a jet can be a plain throttle and a car can ignore drag. A reference sim measures every effect it can against published data and lists each gap, not only the largest; a fix adds or corrects that effect as an optional term and leaves existing games' choices alone. Reference sims live in `scripts/reference/`, outside the runtime packages, and a new one lands only with the game that uses its effect.
- **Respect layering** ([README.md](README.md#layering)). `core` never depends on frameworks, rendering, browser, backend or game code.
- **Scale by default.** Serializable state, injected deterministic randomness, bounded work, allocation-aware hot paths, no full-world per-frame scans, no single-player-only contracts.
- **Stateful primitives keep state, storage and policy reachable.** A `create*` factory with mutable state exposes `snapshot()`/`state()` and `restore()`/`reset()` (`cards/cardPile.ts`), takes storage as an injected interface (`game/keyValueStore.ts`), and keeps play-time values retunable (`vehicleDynamics.ts` `retune`). `check stateful-ratchet` enforces the first.
- **Types are the first test.** `core`, `shell` and `ws` type-check with `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noPropertyAccessFromIndexSignature` and `noImplicitReturns` on top of `strict`. Fix an error with a guard, a real type or a `T | undefined` helper, never `any`, `!`, `as` or `@ts-ignore`; `check type-escapes` fails a file that gains one, and `bun run gen` lowers the committed count. An escape that truly cannot be avoided says `// type-escape: <why>` on its line.
- **Games own their UI composition; the engine ships the parts.** Inventory, windows, vitals, action bars, currency and minimaps are `packages/*` blocks (`HudSlots` plus `@jgengine/core/hud/kitHud.view`) reskinned with the UI kit's tokens. Every game has its own look, a real main menu, a settings surface and in-game credits.
- **Never use Kenney assets.** Prefer Quaternius or KayKit (3D), game-icons.net (icons), ambientCG (PBR).
- **Ports copy behavior and data, not implementation.** Credit sources in `CREDITS.md` and, for player-facing work, in the HUD and website.

## Layout

- **One feature, one folder.** A feature's model, view, draw code and tests live together in `packages/core/src/<feature>/`; the file name says the layer: `hudLayout.ts` (model), `kitHud.view.tsx` (React UI), `WorldHud.draw.tsx` (three.js). A sub-feature nests in its parent's folder. `check layers` enforces the layers ([README.md](README.md#layering)).
- `packages/shell` and `packages/react` hold only package glue: entry points, providers, stores, the game player, its frame drivers and the scene roots that mount core features (`shell/src/world`). Every feature, world and render ones included, lives in its core folder; a new one starts there.
- **Names say what the thing is**: `notificationCenter.ts`, not `store.ts` or `utils.ts`. One exported name has one definition engine-wide.
- **The folders are the map.** No hand-kept concept list; `bun run find <words>` reads folders, exports and doc lines and names the feature folder. Moving a concept home: move its files, delete duplicates, fix every importer and game in the same PR.
- `check concept-homes` (in `verify:fast` and CI) fails a branch that adds an exported name already defined elsewhere (a game export named like an engine export counts: import the engine's, or give the game's thing its own name), or a file named for a concept outside that concept's folder, including a react or shell file for a feature whose folder already holds view or draw files (`// home-ok: <reason>` exempts one). `--all` prints today's duplicates as a worklist.

## Game changes improve the framework

0. **Plan first.** A new game or big feature starts with the [`create-game-jg`](.claude/skills/create-game-jg/SKILL.md) skill: agree the direction with Jon or the user (references, how faithful, breadth, look, scale, players, platforms, what done means), map every feature with one `bun run jgengine has <feature> ...` call, write `games/<id>/PLAN.md` (direction, features with engine owners, gaps, milestones that each add the next 10 minutes of play), then `jgengine create` and build milestone by milestone. Milestone 1 is the core loop playing from second 0; the design brief `check games-design` reads is written once that plays, from what it taught, and is the gate for milestone 2 onward. A milestone is a commit on the idea's branch that ticks it in `PLAN.md`, not a PR of its own; a changed goal changes the plan first.
1. Separate the game's rules, content and presentation from reusable behavior.
2. Check engine `beta` before declaring a gap; if the fix exists, adopt it.
3. Ship the milestone first. A mechanism only one game wants stays in that game with a first-line `// framework-ok: <reason>` and an issue naming the seam; the second game that wants it builds it upstream as the general systems it is made of, with each game's numbers and names in its config, keeping their behavior. A milestone never waits for engine work it can ship without. Do not edit files another session owns.
4. Land the engine change and the game change in one PR. Games run engine source from the same commit, so npm releases never gate a games change.
5. Delete the superseded game-local code. Report the shared owner, the cleanup and the behavior verified.

Repeated glue is a framework defect even when the game works. Games-side rules (size signal, seam line, capabilities ledger) are in [games/AGENTS.md](games/AGENTS.md#framework-first-development).

**No legacy code.** An engine change that breaks an in-repo game fixes that game in the same PR and deletes the old API there: no shims, no deprecated aliases.
Outside users are protected by npm versions only: a breaking change gets a semver bump and a short migration note in `changes/`.

## Runtime and verification

- Cold checkout: `bun run agent:bootstrap` (lock-guarded; `--check` confirms). Never kill a slow `bun install`. Docs-only work needs no install.
- Tests, type-checks and `bun run gen` read package source; `bun run build` is only for packing and the Node CLI.
- Root commands are one per tool; `bun run <tool> --help` lists its verbs and flags. `check [name...]` runs every CI check or the named ones (`--list` names them, `--sdk` is the release set), `gen` regenerates every committed artifact, `test` runs every suite, and `worktree`, `background`, `perf` and `games:capabilities` take a verb. Each check, generator and verb is one row in `scripts/run-stages.ts` or its dispatcher; add a row, never a root script.
- Package scripts: `bun --cwd=packages/<pkg> run <script>`. The space form silently runs nothing.
- Worktrees: `bun run worktree new <name>` (or `claude --worktree <name>`) under the main checkout's `.claude/worktrees/`, never nested, never under `C:\tmp`. While its `bun.lock` matches the main checkout's and the main checkout's install has every package the worktree's `package.json` files declare, it shares that install instead of installing its own, so it is ready in about 10s; a package any `package.json` declares but the tree cannot resolve (a branch checked out after the install) is installed by the next test, check, preflight or `agent:bootstrap`, never reported as ready; to add or change a dependency, first remove the worktree's `node_modules` link (`rm node_modules`, the link only), so the install writes the worktree's own copy and not the shared one. A worktree whose lock has moved gets its own install at the next test or preflight. It also links every game's `public/` packs from one shared store, `<main checkout>/.asset-store` (`JG_ASSET_STORE` overrides), so a worktree downloads nothing. A missing pack: `bun run games:provision [<game>]` links it, or downloads it into the store once per machine. `bun run worktree doctor` finds broken worktrees (`--repair --only <name>`); `worktree reap` removes merged ones, and ones that never committed and sat untouched for an hour. Your own scratch files go in the session scratchpad, never the repo; `.scratch/` is only where tools write their output (logs, perf runs, proof bundles, test fixtures).
- Windows: Git Bash has no `python3` (use `python`; set `PYTHONUTF8=1`, and pass `newline='
'` when writing files). Scripts spawn System32 `tar.exe`, which takes `C:` paths; GNU tar in Git Bash needs `--force-local`.
- Search with `bun run find <words>` (where a concept lives) or `bun run find --text <regex> [--in <dir>] [--files]`, never a recursive listing; `check recursive-walk` enforces it (`// walk-ok: <reason>`).
- One verification pass: `bun run lane:close` runs `bun run preflight` (install, `gen`, then the type-checks and every gate CI's `quick` and `types` jobs run, all of them, so every failure is named in one pass) and then `verify:fast`'s tests itself before it lands, so nothing runs by hand before it. `bun run preflight` alone shows those cheap failures in a minute or two. A CI gate preflight skips is listed with its reason in `CI_ONLY_GATES` (`scripts/verify-fast.ts`). While iterating, `bun run verify:fast` is the same check in seconds (exit 2: a changed runtime file reached no test; a file is covered when its package's suite runs, and pure renames and demos need none). It prints each failing file's first error and writes UTF-8 logs to `.scratch/verify-fast/`; it also runs capabilities-sync and boot-probes the games a change reaches, because CI never downloads models or boots a game. It runs what the import graph reaches and skips a unit that passed with the same inputs (`--no-cache` runs all). Run `bun run verify:fast --full` only to reproduce a CI failure.
- Screenshots back pixel claims: `bun run shoot` or `bun run drive <game> --flow <name>` per `jgengine-verify`, never a hand-rolled Vite app. After two capture failures, report lower-rung evidence.

## Change governance

- **One idea, one branch, one PR.** An idea is what Jon (or the brief) asked for in one go: a feature, a game's milestones, a fix and the cleanup it implies, the engine seam and every game that adopts it. It gets one worktree and one branch from current `origin/beta`, many commits, and one landing at the end. Never split an idea into PRs by milestone, package, issue or step: every PR pays a full landing and rebases against every other. Only an unrelated finding becomes its own idea (file an issue, or a second branch when Jon asks). Never stack on a merged branch or discard unrelated changes; follow the `workflow` skill.
- **Commit as you go**: after each step that works, `git add <its paths>` and `git commit -m "<one plain line of what changed>"` (`Fixed:` / `Added:` / `Removed:` pick the heading). Those lines are the PR body: `lane:close` with no `-m` writes the note from them.
- A helper session given part of someone else's idea works in its own worktree on a branch from the idea's branch, commits and pushes, and does not land; the idea's owner merges that branch into the idea's and lands once.
- **Land once, at the end, with `bun run lane:close`** (add `-m "<what changed>"` to say it in other words than the commits): `preflight`, `verify:fast`, then commit, push, rebase, PR and hand-off to the merge queue — the only landing command. It takes several minutes: run it in the foreground with a 10-minute timeout, and if the shell moves it to the background, wait for it. **The idea is done when its PR is merged**: lane:close's last line names `bun run background await <id> --timeout 540`; run it in the foreground (again if it is still waiting) and report the merge, or fix what it names on the same branch and close again. The repo's Stop hook refuses to end a turn while lane:close or that queue is still running. It regenerates derived files itself, so a stale manifest or ledger never fails a landing, and writes `changes/<branch>.md` (the commit message, PR body and release note) from the `-m` lines, else from the branch's commit messages, bodies included, so a lane never hand-writes one; closing again keeps the note, and new `-m` lines are added to it (to reword a line, edit `changes/<branch>.md` and close without `-m`). Its PR body gets a `## Bends` section only when the diff deletes an assertion, skips a test or disables a check. Rebases are land's and the queue's job, never a lane's: a conflict in a generated file (each `gen` target's `outputs` in `scripts/run-stages.ts`) takes the base's copy and is regenerated, `CREDITS.md` merges both sides' additions, and only a source conflict comes back to the lane. Editing a PR body starts no CI run, and a run cancelled before a verdict is rerun by the queue, never read as a failure. Several finished branches: `bun run lane:close --batch <branch ...>`; `bun run lane:close --queue` drains the queue. Docs-only changes may push to `beta` directly. Never open task PRs into `main`.
- **Never watch CI or sleep.** `bun run ci:status` reads checks once; the queue does the waiting. Every command gets a timeout under 10 minutes. A wait that ends within that (a test run, a landing, `background await`) runs in the foreground with the timeout; only dev servers and game launches run in the background (the harness background, or `bun run background start <cmd>`), never inside a foreground command: a foreground command whose child stays alive never returns. `check no-blocking-wait` enforces no sleeps in code (`// wait-ok: <reason>`).
- **One heavy job at a time per session, and the PC is shared.** Never fan out with `&`, parallel loops or several background starts: one fit, sweep, bake or suite runs at a time, with `--workers` (or its equivalent) at 4 or fewer. A job too slow that way gets a smaller input or a faster tool, never more processes. Stop every process you started before you end your turn, dev servers and browsers included.
- For a reversible choice, pick your recommendation, note it in the PR and continue. Ask only for irreversible actions, money or production data. Record demo clips yourself; keep PR bodies current.
- **Releases** are agent-owned, for outside users, about once a day at most. Check no open PR touches the version, `bun run release` on a fresh branch, land it, `git push origin origin/beta:main`, then confirm the Publish run and `npm view @jgengine/core version`. `bun run release --wait` does all of that, waiting (up to 20 minutes) until npm serves every lockstep package, and then deploys jgengine.com from the released commit on this machine. The deploy builds in its own worktree at that commit, removed afterwards, so the folder the release ran in does not matter (`bun run deploy:site` alone deploys HEAD the same way: provision models, then apps/web's `deploy:cloudflare`). `bun run release --wait <version>` waits on a version already cut and deploys it the same way. A failed deploy fails the release; run that command again to retry it. `publish.yml` refuses commits CI did not pass.
- A bugfix ships a regression test when one is cheap. Do not add new `check-*` gates: a gate costs every lane on every landing, and a rule here is enough for a one-off.
- Rendered changes embed before/after screenshots; behavior over time is shown by driving the game (`jgengine-verify`, `scripts/pr-video.ts`).
- API, workflow or tooling changes update their skill and generated artifacts in the same PR. Findings go in the issue or PR and a game's build plan in its `PLAN.md`; `check skills` fails markdown outside this file, READMEs, skills, `changes/` and `examples/`.

`jgengine` is intake and routing only; load only the domains a task needs (`capabilities.md`, generated `api.md`, references). One owner per concept: `workflow` delivery, `jgengine-verify` evidence, `improve` backlog passes, `ce-handoff` continuity. Claude Code reads this file; `CLAUDE.md` must not exist.
