# JGengine repository governance

[README.md](README.md) owns stable project truth: repository map, packages, layering, stack, commands, publishing model and license. Read it and whatever the change touches; do not restate its facts here or in skills. Explicit user instructions take precedence over this file and over any skill. If a skill makes you pause, ask for confirmation, or leave requested work unfinished, name and link its SKILL.md and continue with the user's instruction.

## Project purpose

JGengine is developed through distinct playable reference games. Playing and inspecting them reveals missing or broken framework capabilities, including layout, input, rendering, asset placement and physics. The purpose of a game review is to improve the shared framework so every applicable game benefits from one correction.

Before fixing a symptom in a game, trace its cause to the installed SDK contract, its adoption or the game's own rules and composition. Reproduce a framework gap upstream, fix its shared owner, verify the packaged behavior in the affected game and a differently composed consumer when applicable, then remove superseded game workarounds. A fix copied into each game is unfinished framework work.

Games own unique rules, content, assets, art direction and composition. Keep those choices distinct and shared behavior configurable. Diagnose the actual cause: an obstructed HUD does not automatically justify game-local CSS, and apparent sinking does not justify a guessed model offset. Report the framework gap resolved and behavior verified, alongside game-specific improvements and remaining gaps.

## Writing

Write short, everywhere a human reads: chat replies, PR bodies, issues, commit messages, review replies. One idea per line. A chat reply is what you did, what is still open, and the links; if it runs past a phone screen, cut it. A PR body is a line of context, a bullet per changed area, `Closes #N`, verification as command names with their verdict, and screenshots; a bugfix adds one sentence of root cause. An issue is the problem in a sentence plus acceptance criteria. Leave out plan recaps, what you considered and rejected, per-file walkthroughs, restated tool output, closing summaries, apologies and offers of more help. Expand only when asked to explain or why, and then answer that question and stop. A decision that needs the user is one concrete question with the options named.

Use plain, literal, conversational language in the tone of a calm coworker. Keep facts, assumptions and suggestions separate and say what you are unsure of. Rewrite any sentence that reads like a slogan, a trailer line, a pitch deck or an argument.

Define a term in the sentence that introduces it, or do not introduce it; use the user's own vocabulary for their domain. Ask decisions, not worries: name the decision and the options rather than thinking aloud with a question mark. Propose the frame before building the artifact: ten lines showing the shape catches a wrong premise before hundreds of lines exist. A merge is not approval and silence is not agreement; when a user rejects a name, ask whether the thing survives before renaming it.

Code comments default to none. JSDoc on exported public API stays, since it generates `api.md` and `capabilities.md`, and it stays tight. Inside a function body a comment earns its line only for a non-obvious why: a workaround, an invariant the types cannot express, a formula's source, a deliberate tradeoff. Delete restatements of the next line, section banners, step numbering, unlinked TODOs, commented-out code and changelog notes. Match the density of the file you are editing.

## Product invariants

- **World content is authored in the editor.** Scenes, placement, terrain, paths, zones, foliage and assets live in `editor.scene.json`, authored through the editor GUI or RPC/CLI. Any request that adds, moves, restyles or removes visible world content is an editor authoring task first; runtime and gameplay consume that document through shared primitives. If the editor cannot express the content, file a `[FEATURE]` issue before any code fallback and never hardcode geometry or coordinate arrays a scene can own. `jgengine-editor` covers authoring and `jgengine-world` runtime consumption.
- **Reusable capability goes upstream first.** Before editing a game, search the installed SDK and name the shared owner. Adopt an existing capability; fix or extend its package when its contract is insufficient. Anything another game could need belongs in `packages/*` as a narrow, configurable seam with a real game adopter. Do not patch each game separately or copy engine behavior into a local helper. Recipes compose SDK APIs; they do not replace reusable implementations. Extracting a primitive preserves observable play.
- **Every game is custom; there are no genre kits.** Never build or reach for kits, presets, archetypes or "default sports car / RPG / FPS" shapes in the SDK or skills. Probe games are probes, never templates; prefer `capabilities.md`, recipes or core APIs over another game's source. When two custom games would re-handroll the same behavior, that behavior belongs in the SDK; recipes show how to compose it.
- **Respect package layering.** The dependency direction in [README.md](README.md#layering) is authoritative. Never import from a higher layer or make `core` depend on frameworks, rendering, browser, backend or game code.
- **Scale by default.** Prefer serializable state, deterministic injected randomness, bounded work and allocation-aware hot paths. Avoid full-world per-frame scans and single-player-only contracts.
- **Stateful primitives keep state, storage and policy reachable.** A `create*` factory that owns mutable state exposes a state-out method (`snapshot()`/`state()`) and its counterpart (`restore(next)`/`reset(next)`), as `cards/cardPile.ts` does; takes its storage as a narrow injected interface, as `game/keyValueStore.ts` and `combat/magazine.ts` do; and keeps anything that changes during play retunable, as `physics/kinematicVehicle.ts` `retune` and `combat/abilityKit.ts` `retuneSlot` do. `check-stateful-ratchet` enforces the first; review covers the other two. Policy a game might vary is a callback or config field, never welded in.
- **Every game owns its UI composition; the engine ships the common parts.** Inventory grids with real drag/stack/split, toggleable windows, vitals and stat bars, action bars, currency counters and minimaps ship in `packages/*` as drop-in blocks a game wires and reskins with HudTheme tokens; reaching for them is correct use. Games own the overall look, layout, terminology, a real main menu, a settings surface and in-game credits. Judge UI by the rendered result.
- **Never use Kenney assets.** Prefer Quaternius or KayKit for CC0 3D, game-icons.net for icons and ambientCG for PBR.
- **Ports copy behavior and data, not implementation.** Harvest numbers, tables, layouts, palettes, formulas and feel, then rebuild on engine seams. Credit inspiration, ports and copied permissive assets in `CREDITS.md`; player-facing work also carries HUD and website credit.

## Game changes improve the framework

1. Separate unique game rules/content/presentation from reusable behavior. Rendering lifecycle, input, storage, interaction, UI accessibility and authoring machinery have shared package owners.
2. Check the installed version before declaring an engine gap. If a fix already exists upstream, plan its published adoption and remove the obsolete workaround instead of implementing it again.
3. Implement missing shared behavior upstream with configurable policy, preserving the first adopter's behavior and identity. Coordinate a differently composed second consumer when applicable; do not edit another agent's owned files.
4. Verify the packaged API, then adopt it: unreleased work by pinning its commit in `JGengine-games` (`bun run engine:pin --ref <sha>`), a published version in the games root workspace catalog and lockfile together, never in individual game versions. A beta merge does not update installed games, and a publish is not needed to adopt one. Change governance below owns releasing it.
5. Delete superseded game-local algorithms, listeners and resource management after adoption. Report the shared owner, consumer cleanup and actual behavior verified; line counts alone are not a quality measure.

Repeated glue is a framework defect or adoption debt, even when the game works. A tracked fallback records its upstream gap and removal path; it is not a completed reusable capability. Shared behavior must allow distinct game art and rules, not force identical assets, layouts or genre presets.

## Runtime and verification

A cold checkout needs `bun run agent:bootstrap` before commands that need dependencies (lock-guarded, so re-invoking joins the running one). On Claude cloud sessions it starts automatically; confirm with `bun run agent:bootstrap --check`. Never kill a slow install: a killed `bun install` forces a wipe-and-reinstall loop. Inside the monorepo, tests, type-checks and `bun run gen` resolve `@jgengine/*` to package source through the tsconfig `paths` in `tsconfig.base.json` (kept in sync by `bun run gen:source-paths`), so no build is needed; `bun run build` is only for packing, publishing and the Node-run CLI. Read-only and documentation work does not need any of it.

Run package scripts as `bun --cwd=packages/<pkg> run <script>` (the `=` form). The space form prints bun-run help and exits 0 without running anything, and `bun run --cwd` can hit the wrong root script.

Worktrees are for agents sharing one filesystem, local or cloud: `bun run agent:worktree -- <name>` or `claude --worktree <name>`, both under the main checkout's `.claude/worktrees/`, never nested and never under `C:\tmp`. `agent:worktree` links dependencies, `Games` and the dev runner's ignored assets from the main checkout, so the tree is clean and `bun run shoot` works without a build. Scratch and evidence go in `.scratch/`, which never holds a checkout. A lone cloud session is already isolated; branch from `origin/beta` there.

`bun run worktree:doctor` prints every worktree's install in both repos, worst first, and exits 1 while one is broken; `--repair --only <name>` reinstalls the broken ones it can safely touch. A filling disk leaves `node_modules` half-linked, which a bare `bun install` will not repair: the doctor deletes that tree's store and installs again, only in a clean tree.

`bun run worktree:reap` removes every worktree whose branch has merged into `origin/beta` and whose tree is clean; a locked, detached, unmerged or dirty tree is kept and named. `lane:close` and `agent:worktree` run it, so a closed lane's copy goes instead of accumulating one working copy per lane.

`bun run lane:audit --hours 40` accounts every child session in the window: span, minutes inside tool calls, minutes in sleep/poll loops, minutes watching CI, and the three slowest commands, with each lane's waiting minutes ranked against the window's other lanes. Read your own row before reporting; `--json` gives the same numbers to a script, `--cwd <dir>` narrows to one lane and `--fail-on-waiting` exits 2 on any sleep or CI watch. `bun run check:no-blocking-wait` fails a `scripts/**` or `packages/**` file that runs `gh run watch`, `gh pr checks --watch`, `Start-Sleep`, `sleep` or `timeout /t`; a wait that is genuinely required carries `// wait-ok: <reason>` on the line or above it.

Search with `bun run find <pattern> [--in <dir>] [--kind ts,tsx] [--files]`, never a recursive directory listing: ripgrep reads the tree once and never enters `node_modules`, `.git`, `.claude/worktrees` or build output, where a tree walk took 160 s and timed out eight calls in three hours. `--files` lists names by `--glob`; `bun run check-recursive-walk` fails a script or lane document that ships a recursive walk, and a required one carries `// walk-ok: <reason>`.

Local tests, typechecks and `ship:preflight` run without asking; fix what the change broke and rerun the affected checks. Deterministic tests come first. Before pushing, run `bun run verify:fast` - seconds, because it maps the branch diff against `origin/beta` to the packages, tests and `quick` static gates that reach it, and exit 2 means a changed runtime file reached no test - then `bun run gen` when public API changed and `ship:preflight`. `bun run land` waits for PR CI itself, so do not run `bun run gate` locally unless you changed the gate itself or CI failed and you need to reproduce it. Screenshots are for pixel claims, captured with `bun run shoot` or a step file (`bun run drive <game> --steps <file>`, `--check` lists the steps without running them) per `jgengine-verify`, never a hand-rolled Vite app; a step states a condition before and after each action instead of a guessed `--wait`. Arbitrary `--url` pages declare `document.documentElement.dataset.jgCapture = "ready"` only after an honest rendered frame. After two capture failures, stop and report lower-rung evidence.

## Change governance

Start a task branch from current `origin/beta`; never stack new work on a parked or merged branch, and never discard unrelated changes. Read what the smallest end-to-end change needs, then act; recon ends in a commit. Close tracked issues from the PR with `Closes #N`. Post a one-line claim comment on an issue only when no one assigned it to you; an issue handed to this session by the user or a parent session is already claimed.

A PR is one coherent, independently reviewable and revertible change. Combine work that shares a root cause, API migration, files or verification story; split work that is independently releasable or likely to conflict. Issue count never determines PR count. Follow the `workflow` skill for issue → change → verify → ship and push with a standalone `git push`. Work lands on `beta` with `bun run lane:close`: it runs `bun run verify:fast`, lands the branch with `bun run land` (push, rebase onto `beta`, open or reuse the PR, wait for checks, merge, confirm MERGED), asks the checks once, then refuses a lane that slept or watched. When several finished, independent branches are ready together, `bun run land:batch <branch ...>` merges each onto the growing `beta` tip in order, verifies every merge, skips a branch that conflicts or fails instead of pushing it, and pushes the survivors in one push so CI runs once; `bun run land:batch --explain` names the commit a red batch tip most likely came from. Push a docs-only change to `beta` directly. The user never merges by hand. Never open task PRs into `main` and never enable auto-merge for another owner's repo. Agents own releases; the user never cuts, approves or times one. Publishing is a milestone, not a step after each change: at most about one a day, or when a game ships to someone outside this machine. A lane takes merged, unreleased engine work by pinning the commit in `JGengine-games` (`bun run engine:pin --ref <sha>`), which needs no publish and no pin PR. Release when the batch is done and proved, a game needs a version to hand someone, or the pins have drifted far enough to be worth collapsing, and for nothing else: publishing per change is what shipped 0.38.2, a patch that narrowed two public types because one lane needed one field. Check no open PR touches the version, run `bun run release` on a fresh branch from `origin/beta`, open and merge that PR like any other, fast-forward `main` with `git push origin origin/beta:main`, then confirm the Publish run succeeds and `npm view @jgengine/core version` shows the new version. A game that ships takes the published version into its root catalog and lockfile together, merges, and fast-forwards its `stable` to `beta`. This repo's own pin moves separately with `bun run games:bump` in a PR of its own. `main` moves only through this release flow; `publish.yml` starts from the `main` CI run of that commit and refuses one CI did not pass, so a release never re-runs the suite and a flaky test cannot block it. It publishes only after `bun run check:consumer-types` packs the candidate, installs those tarballs into the pinned `JGengine-games` checkout and compiles it: a type error names the game package, file and line, and a run that could not check at all (no games checkout, failed install) stops the release the same way. This paragraph is the one owner of the merge and release policy; skills link here instead of restating it.

Never subscribe to a PR's activity or watch CI: `bun run ci:status` answers the checks in a second and `bun run land` waits for them. A command that outlives the call that started it goes in the background: the harness's own background execution first, else `bun run bg:run -- <command>` for the id and `bun run bg:await <id>`, which returns on the exit event with the output and the exit code. `bun run pr:sweep` lists every open PR armed for auto-merge that cannot merge and names the check that blocks it, exiting non-zero while any is red. Ask again in a later turn. For a reversible choice, pick the option you would recommend, say which in the PR body, and keep going — ask only for irreversible actions, money or production data; merges and releases are never questions. Record demo clips and videos yourself with the repo's capture tooling; never ask the user to record them. Rewrite a PR body yourself whenever it goes stale.

Public API, workflow, convention or tooling changes update their owning skill, reference and generated artifacts in the same PR. Durable guidance belongs here, in an existing README, or in the owning skill; plans, progress and findings belong in the issue or PR. Never create a `docs/` tree, plans, audits, decision records, logs or other freestanding markdown; `check-skills` fails CI on markdown outside this file, READMEs, skills, `changes/` and `examples/`.

A bugfix PR body (never a feature PR) answers which engine seam, permissive default or missing contract allowed the bug, whether another consumer could hit the same class (if so the systemic fix goes upstream into `packages/*` or a gate so silence fails CI), and, when that reinforcement is too big for the fix, which `[FEATURE]` issue tracks it. Prefer making the wrong state unrepresentable over heavy process; one sentence of root cause is the ceiling of ceremony.

**A failure class repeats until a gate exists.** A fix is finished only when the same failure fails loudly next time: a regression test by default, a `check-*` script when the class is structural (`bun run check:fix-has-test` rejects runtime source with no test change unless the body carries `Prevention: none - <reason>`; `bun run check:fixture-location` rejects fixtures built outside the workspace), a CI job when it is platform-specific (`windows-tests` runs the `jgengine` package suite on `beta`). Advice in a document is not prevention.

Completion is an evidence claim: inspect the diff against the acceptance criteria. Changes to a rendered surface embed before/after screenshots or a short capture in the PR body; skip only when there is genuinely no rendered surface, and say why. The PR body carries evidence, not a transcript. Behavior over time gets tried by driving the actual game, presented as video or stills, never a GIF and never a video file in the conversation; `jgengine-verify` covers recording and `pr-video`.

When a task has two or more legs that do not need each other's output, delegate them to parallel subagents with disjoint files and judge their evidence rather than trusting claims; keep planning, overlapping edits and synthesis in the main agent. Route long mechanical sequences (regenerating artifacts, mass renames from an explicit list) to the cheapest capable model with exact commands and success criteria, and keep design, debugging and code authorship on the strongest available model.

## Skill architecture

`jgengine` is intake and routing only. Load only the domains the task needs; use each domain's `capabilities.md` for intent-to-import discovery, `api.md` for the generated export inventory, and references for deeper workflows. Each concept has one skill owner: `workflow` owns delivery, `jgengine-verify` owns evidence, `improve` owns backlog passes and post-fix retrospectives, `ce-handoff` owns session continuity, and domain skills own their package boundaries. Skill descriptions stay short and trigger-oriented; `SKILL.md` holds decisions and canonical workflows, not export catalogs or repeated project facts. Claude Code reads this file directly; the repository gates that no `CLAUDE.md` exists, route integrity and duplicate prose.
