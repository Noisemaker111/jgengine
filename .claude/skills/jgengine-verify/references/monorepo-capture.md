# Monorepo capture toolkit

Deep reference for `shoot`/`drive` inside the jgengine monorepo: the managed capture session, aiming flags, recording, PR media, and capture-stack behavior. The evidence rules and the screenshot bar live in [SKILL.md](../SKILL.md); a created standalone game uses the portable `bun run shoot` / `bun run drive` described there.

## Managed capture session

1. Run `bun run shoot daemon start`. Startup keeps only headless Chrome warm; `apps/dev` and `apps/web` start lazily on first use and then remain warm. A non-zero exit means capture is unavailable, not permission to repeat cold launches.
2. Capture games with `bun run shoot <game> --mode play --size half --inspect`. Capture real website routes directly with `bun run shoot --site '/playground?...' --size half --inspect`; `--site` uses managed `apps/web` and does not build or boot the embedded `/play` runner unless `/play` is requested.
3. Record game or website behavior with the same browser: `bun run drive <game> ... --record <name>` or `bun run drive --site '/playground?...' --wait 1000 --record <name>`. `drive --site` writes `shots/site-<name>.mp4`; present the MP4 or representative stills, never the generated GIF.
4. Every invocation opens and closes a fresh page target while retaining process-level V8, HTTP, module, shader, and Vite caches. Editing code while the daemon stays live is supported; a stale-shaped post-HMR failure gets one cache-bypassed retry without restarting the daemon.
5. Changing *commit* under a warm server is not an edit HMR can absorb, so a warm Vite is keyed to the commit it booted from: `shoot`/`drive` retire it, clear the dep-optimizer cache, and boot a clean one whenever HEAD has moved. Never stop the daemon or delete `node_modules/.vite` by hand for this — if you are doing that, the capture stack has a bug worth fixing instead.
6. Reject blank, sparse, overflow, and collision failures before opening the PNG. Capture the final accepted state at full resolution, embed screenshots with `bun run pr-shots`, and stop the session with `bun run shoot daemon stop` when the loop ends.

Do not run bare cold `shoot` or `drive` repeatedly in a multi-shot loop. For a single proof where persistent processes are undesirable, one ephemeral invocation is supported and cleans up Chrome/Vite afterward; measured local evidence for `/playground` is roughly 12 seconds cold wall time and 3 seconds inside the browser. If managed capture fails twice, stop retrying and report lower-rung deterministic evidence.

## Aiming, spawn, and named views

- Engine preview fixtures (the real exported `@jgengine/react` primitives — `HudThemePreview`, `BarsPreview`, `IconsPreview`, …) capture with `bun run shoot --fixture <name>` — no game boot, no hand-rolled `--url` page. `bun run shoot --list` (or `--fixture` with no name) prints the registered set; an unknown name reports the available fixtures. The runner mounts them from a `?fixture=<name>` overlay; the set lives in `@jgengine/react`'s `PREVIEW_FIXTURES` registry, so registering a new deterministic preview component there makes it capturable with no harness change. Use this to screenshot shipped HUD building blocks deterministically instead of booting a full game.
- Per-shot player spawn: `bun run shoot <game> --spawn x,y,z` (or `drive --spawn`, or a `?spawn=x,y,z` URL overlay, mirroring `?cam=`) relocates the player for that capture only — the play camera follows, so a close-up frames the new vantage — **without editing `editor.scene.json`**. Accepts `x,y,z` or `x,y,z,yaw` (yaw radians); it overrides only the default `player_spawn` (an explicit marker id/kind is untouched). Prove non-mutation by checking the scene file's `git status` stays clean after the run. Use it instead of hand-editing and restoring the scene document.
- Aim at a place, not a player: `bun run shoot <game> --look x,z` (or `drive --look`, or a `?look=` URL overlay) pins a detached camera on a world point — ground height is looked up, so pass the XZ you already have from `editor.scene.json`. `--look x,y,z` takes a point in the air instead, and the vantage is a second flag: `--look-from dist[,height[,angle]]` (default `12,5,0`, angle in radians). **Reach for this before `--spawn` whenever the subject is a place.** `--spawn` moves the player but does not pin look yaw, and anything that walks has walked by the time the frame settles, so aiming by spawn is a coin flip that costs a capture round per attempt; `--look` frames the same coordinate every run. The game's own `WorldOverlay` (a viewmodel, say) still draws — that is game content, not the rig.
- Re-capture a framing by name: a game declares `capture.views` (sibling of `capture.states`) and `bun run shoot <game> --view <name>` replays that camera, staging, and settle exactly — so a before/after pair is the same view by construction instead of two hand-typed flag sets that drifted. `bun run shoot <game> --list-views` prints what a game declares; an unknown name fails listing them. Any explicit flag still wins over the view's value (`--view keep-enemy --look-from 60,28` keeps the marker, changes the vantage). `drive --view <name>` takes the same framings — note `drive --shot` still names the *output file*, so `drive <game> --view keep-enemy --shot before` reads as it looks. Declare a view for anything a reviewer asks about twice.
- Aim by name, not by coordinate, whenever the subject has an id: `--look @marker:<id>` resolves against the authored `editor.scene.json` (and stays correct when the scene moves), `--look @entity:<id>` binds the observer rig to a live entity so the shot tracks whatever walks. Both take `--look-from` like a coordinate aim, and a marker gets the same terrain clearance. A wrong marker id fails listing every marker in the scene; a wrong entity id fails once the context is live rather than quietly framing the world origin.
- A bad aim fails the capture; it never returns a plausible wrong frame. A malformed coordinate, an aim outside the world bounds, or a vantage the terrain would bury errors out naming the reason, and an accepted aim prints `shoot: look applied {...}` with the resolved target and camera. Never hand-tune `--settle` to chase a half-empty establishing shot — readiness already waits for model streaming to go idle; if a frame still looks wrong, read the forwarded `page warning:` lines, which carry the engine's own camera and asset diagnostics.
- Editor/district aerials in one call: `camera_goto`/`camera_frame` take `distance`, `pitch` (degrees above the horizon; 90 = straight-down), `yaw`, and `height`, so `bun run drive <game> --mode editor --rpc '{"method":"camera_frame","pitch":70}' --shot aerial` frames the whole document from above with an auto-fit distance — no KeyF-buries-in-terrain and no guess-the-y-offset round-trips. Pin a spot + pose with `--rpc '{"method":"camera_goto","x":40,"z":-20,"distance":80,"pitch":55}'`. The RPC response echoes the resolved `target` (with `distance`/`pitch`) as the numeric proof the pose changed.

## Driving, probes, and recording

- `bun run drive <game> --wait ... --rpc ... --key ...` scripts the browser drive headlessly; `drive --playtest` with a declared capture probe is the softlock/progress rung for interactive loops. On a **software-GL host** (cloud SwiftShader — Linux/CI headless runs at a fraction of 1fps) a held key barely advances the sim, so a flat probe cannot be told from a genuine softlock: `--playtest` now detects the software renderer / low effective fps, reports the run as `UNRELIABLE` instead of a false `SOFTLOCK`, does **not** fail even under `--strict`, and points you at the deterministic rung — step the sim directly with `stepPlayerMovement` / `createHeadlessRunner(...).step(1/60)` (rung 4 above) for a trustworthy verdict. The verdict JSON carries `effectiveFps`, `softwareGl`, and `renderer` so you can see why. The perf sequence above becomes one command: `bun run drive <game> --wait <load+warmup> --rpc '{"method":"debug_perf_reset"}' --key KeyW:4000 --wait 10000 --rpc '{"method":"debug_snapshot"}'`. Drive's `--mode play` captures live integration; preview states capture deterministic HUD/menus.
- Movement/held-input claims: `drive` focuses the game surface before every `--key` hold (play-mode keys are a React `onKeyDown` on the canvas wrapper, dead unless that element is `document.activeElement` — a prior `--click` moves focus off it) and holds the key across at least one rendered frame, so a held key advances the sim even on a slow software-GL page. Prove movement with `--probe`, which prints the game's live `capture.probe` metrics (declare one that returns player x/y/z): `bun run drive <game> --probe before --key KeyW:20000 --probe after` — a non-zero position delta between the two reads is the honest check. Judge movement by that RPC delta, **not** by screenshot diffs: headless GL here runs at a fraction of 1 fps, so a real held key moves the player only a little per second and before/after frames can look identical while the delta is clearly non-zero.
- Recorded clips: `bun run drive <game> --record <name>` records every rendered frame of the whole drive (CDP screencast) and writes `shots/<game>-<name>.mp4`: the full-fidelity real video — every captured frame, true timing, no size cap. **Present clips as video or still images — never as a GIF** (`--record` still emits a `.gif` alongside the mp4; ignore it — the mp4 is the clip). For GitHub's NATIVE inline player, `bun run pr-video <clip.mp4>` uploads to GitHub's user-attachments store and prints a URL that — pasted on its own bare line in the PR body — renders as a real video player; it requires the `GH_SESSION_TOKEN` env secret (a github.com `user_session` cookie; there is no token API for attachment uploads — see the script header for setup). Where the session's egress policy blocks the `github.com/user-attachments` upload (cloud sessions allow only repository-scoped endpoints), do not give up on the player: push the mp4 with `pr-shots`, then trigger the `pr-video` workflow by posting a comment `/pr-video <clip_path within the pr-shots branch>` on the target PR/issue (the MCP `add_issue_comment` works; direct `actions_run_trigger` dispatch 403s — the integration has no actions:write) — the Actions runner has open egress, uploads, and replies on the same thread with the inline-playing URL; it needs `GH_SESSION_TOKEN` as a repository **Actions** secret (Settings → Secrets and variables → Actions — separate from any agent-environment env var). Only when neither path is available: commit the mp4 and link it as a download, extract representative still frames for the inline evidence, and never fall back to an animated GIF. Recording runs in **lockstep**: the page's rAF/clocks are taken over and game time advances one fixed tick per captured frame, so the clip plays smoothly at `--record-fps` (default 10) no matter how slowly headless software GL renders — but every output frame costs a real render (~2-3s wall each at `--size half`), so choreograph recorded drives in 10-20s of game time and lower `--record-fps` before lengthening them (over ~900 projected frames the drive refuses to start). `--record-realtime` keeps the old capture-what-actually-rendered screencast (~1fps here) for honest performance evidence. A clip is prosecuted like any screenshot: extract or step through frames, and pair it with `--probe` deltas — the probe proves the physics, the clip shows it.

## PR media

- Visual PRs embed final screenshots with `bun run pr-shots`; do not send binary images through GitHub content APIs. Any change to a map, world, or scene document counts as visual: attach captures of the changed content (in-game shots, or a map render derived from the authored document) to the PR and share them in the conversation, not just test assertions. Changes to behavior over time — collision, movement, camera, animation, staged sequences — attach a `drive --record` clip as video or still frames (never a GIF): the native inline player via `pr-video`, else the committed mp4 linked for download plus representative stills. In the conversation share still frames extracted from the clip plus the GitHub link — **never send video files into the chat** (they do not load in the user's client; screenshots do).

## Regression bisect

**Bisecting a visual regression:** `bun run probe <commit> -- <shoot args>` captures one commit into `shots/probe-<short>.png` and restores the ref it started on, reinstalling only when the probed commit moves a manifest or lockfile. Use it instead of hand-running checkout/shoot pairs — a bare `git checkout` between shots is the loop that used to produce mixed-commit frames and readiness timeouts. It refuses to run on a dirty tree, so commit or stash first.

## Capture-stack behavior

Pixels come off the CDP screencast pump rather than a forced `Page.captureScreenshot`: same compositor output, same lossless PNG, but one frame's wait instead of several re-rasters — on this cloud SwiftShader box a full-res `ironhold --mode play` shot went 31s → 12-16s and `wreckway --mode play` 54s → 28s. The forced path stays as the fallback whenever the pump cannot reproduce the shot exactly: a `--device mobile` profile (the pump emits CSS pixels, so a dsf=2 shot would be half resolution), a page that commits no new frame, or `JG_CAPTURE_SCREENCAST=0` to force it by hand. The timing line names which path ran (`frame(screencast)` vs `frame(screenshot)`), so a slow shot says why. One consequence to expect: a faster capture is a shot taken earlier in game time, and a game that spawns its world after `ready` will now frame an emptier field than it used to — the slow encode was silently acting as settle. Declare that wait where it belongs, as `--settle` or a `capture.views` settle, instead of relying on how long a PNG takes.

Local Windows/macOS capture uses native GPU acceleration so WebGL does not saturate the CPU. Linux and CI default to SwiftShader for GPU-less cloud agents; set `JG_CAPTURE_SOFTWARE_GL=0` on a GPU-equipped Linux worker or `JG_CAPTURE_SOFTWARE_GL=1` to force deterministic software GL locally. Cloud images are supported when Chrome/Chromium is installed (`CHROME_PATH` overrides discovery; `/opt/pw-browsers` is detected), and MP4 encoding uses the repository-packaged ffmpeg binary. Website readiness defaults to 10 seconds locally and 30 seconds on Linux/CI.

Navigation failures (`ERR_UNSAFE_PORT`, connection errors), document load failures, and uncaught page exceptions surface immediately with their real cause. They are not stale HMR and must not pay the readiness timeout. The managed website port is selected from Chrome-safe `5517..5916`; an HTTP health check alone does not prove Chrome can navigate a port.

A shot on disk is self-describing, and three mixups are now mechanical failures rather than things to stay alert for:

- **Stale.** `shoot`/`drive` delete the target PNG and its sidecar *before* capturing, so a failed or hung run leaves nothing at that path. A file that exists is a file this run wrote. Never reason about a shot whose command errored — there is no longer a file to reason about.
- **Unchanged.** Every shot writes `<name>.shot.json` (command, timestamp, git HEAD + dirty flag, sha, luminance signature). A re-capture that shows the same picture as the shot it replaced prints `SAME PICTURE as the shot it replaced` — that is a no-op change or the wrong view, not a passing test. Comparison is perceptual, not byte equality: two captures of an unchanged view differ in PNG bytes every time. `pr-shots` refuses to publish duplicate images (`--allow-identical` to override), so a before/after pair that never moved cannot reach a PR body. A change touching only a few coarse cells can read as unchanged — if you know the diff is tiny, check the pixels rather than trusting the verdict.
- **Dead viewport.** Pixel metrics run on every shot now, not only under `--inspect`, and score the 3D viewport with HUD rectangles masked out. A blank or single-flat-fill viewport fails the command. This is the case whole-frame scoring could never see: a busy HUD supplies enough entropy that a frame with nothing rendered still scores `nonblank`. `--inspect` still writes `<name>.metrics.json`, now with `frame` and `viewport` blocks. Games whose overlays are missed by mask discovery can force an element in with `data-jg-capture-mask`.

None of that replaces looking. It removes the failures that survived looking.
