# Perf harness

Detail for the performance rung of `jgengine-verify`. Read it when a claim is about frame time, load or network cost.

## Performance proof

When a game is reported slow, play it and pull the debug menu's perf data instead of guessing.

**A game already open reports on itself.** In a dev build the shell samples frame telemetry in-page — no second process, no CDP: `bun run perf live <game>` prints the newest record for a game open in a browser (about 0.3 s, it only fetches `/__jgengine/report` from the dev server you started with `bun dev`, at `/games/<id>`), `window.__JG.report()` returns the same object from the console, and either fails a budget breach with the same verdicts as CI. It carries `systems` (each core system's own counters, timers and state line via `devtools.probes.registerSystem`) and `logs` (the warning/error ring, kept across a crash or reload by the dev server). The sampler is off in production builds and off under `?telemetry=off` for an A/B run.

In the engine monorepo, `bun run perf <game> [<game> ...] [--quality low|medium|high|ultra] [--seconds n] [--telemetry on|off] [--state name] [--param k=v ...] [--set key=value ...] [--path walk|still] [--size WxH] [--compare <ref|before.json>] [--capped]` does the whole sequence below on a real GPU at 1920x1080, writes the record (with its frame breakdown) to `.scratch/perf/<game>.json` or `--out`, and prints a short text summary (`--json` prints the record instead) — the one to use when you need a profile, a cold launch, or a repeatable GPU measurement rather than the page you are already watching. `--set` seeds a persisted setting before the game boots (`--set colorblind=grayscale`, `--set quality=low`, repeatable; a key is an engine setting id or its last segment, or a setting the game declares in `defineGame({ settings: { extra } })` such as `survey.hints`), so a setting's or graphics option's cost is measured by the harness and the record's `overrides` names what was on. An unknown key or a value the engine or the game does not offer fails the run instead of measuring the default, so compare an override run with a plain one rather than with a budget.

## Where a frame goes, in under 5 minutes

1. `bun run perf <game> --seconds 8` (about 30 s), on a clean tree before you edit, so the run is kept as that commit's baseline. It holds forward and weaves left and right; the saved movement endpoints show whether the player moved overall when the bridge can report them. It prints frame p50/p95/p99 and CPU and GPU time separately. Frame time includes waiting; the larger CPU/GPU figure assumes overlap and does not predict FPS.
2. Read which side is bigger. GPU over CPU: the `gpu` list names the pass (`shadow`, `main`, `post:<Effect>` per post effect, timed with WebGL timer queries; `no timer queries` means the GPU could not be split). CPU over GPU: the `cpu` list is self time per system: `render:<pass>` is three.js walking the scene, `sim:<phase>` and `stage:<id>` are the engine's sim, and `frame#n file:line` is a `useFrame` callback named by where it was written.
3. Read the top objects and materials: draws, triangles and CPU per frame for each, named by the nearest named ancestor (`Rock (InstancedMesh, DodecahedronGeometry) in Boulders #41`). Many draws of one thing: instance or merge it. Many triangles: a lower LOD.
4. Read the hitches: each frame over 33 ms names its cause: `compile` (shader programs compiled, or first used after a link, that frame, with the draw that waited named as `material on object`; warm them at load), `upload` (texture or buffer MB sent to the GPU), `gc` (the heap dropped; allocations in a per-frame path), a CPU system, or a GPU pass. The `gc ~N MB` figure is MB collected over the run.
5. Read the top functions: CPU self time per function from a profile of the same run. A three.js, React or browser function (`projectObject`, `getBufferSubData`) is named with `via`, the engine or game function that called it, which is where the fix goes.
6. Fix one thing, then `bun run perf <game> --seconds 8 --compare HEAD`: the before side is the cached run from step 1 (every run on a tree with no edits to `packages/`, `apps/dev` or that game is kept under `.scratch/perf/baselines/` by commit and run settings), so only the after side is measured. The summary prints before -> after for frame, cost, each system and pass. `--compare <file.json>` compares against a record file instead. Run-to-run noise is 5–15% on p95, so repeat a small win before claiming it.
7. Prove a fix on one game before sweeping. A sweep is `bun run perf <game> <game> ...`: one browser plays them in turn and ends with a table of frame, cost and distance from 144 Hz per game. A game takes about 30 s and a run stops at 7 minutes, so sweep in batches of ten.

The same breakdown is live in any dev build: the debug menu's perf panel shows "where the frame goes" over the last 600 frames, and `window.__jgFrameBreakdown.summary({ last: 600 })` returns it from the console.

The breakdown reports timed scope calls per frame (average and maximum). Render calls include legitimate shadow and post work; a count alone does not establish waste. `bun run perf <game> --param frameMembers=1` times individual shared-frame members and counts instrumented fauna updates, agents, ground queries, ground-revision invalidations and shader readiness checks under their requesting callback. Compare a matching run without that parameter to measure overhead. Other work is unobserved, omitted summary rows are counted, and an unresolved `frame#` remains unattributed. GPU timing covers only completed queries; unavailable timings are not zero. The saved summary is not an exhaustive trace.

The saved record also compares the running dev server's checkout and boot revision with the measuring checkout. `matched` proves that identity only, not that dirty files or compiled assets are byte-identical. A mismatch or unavailable server identity is saved with the run and cannot become a cached baseline. Callback locations use the served source map; a missing map is labeled `generated` and counted as unresolved.

Runs are headless on purpose: headless Chrome draws on the real GPU here, while `--headed` puts an off-screen window under the desktop compositor, so its numbers are not the ones to report.

An A/B of two live gameplay windows measures the scene, not the setting: runs of one build moved harbor-heat between 1172 and 1296 draws (9.5%), so a millisecond-scale effect sat inside that noise. `--state <name>` boots into the game's own `capture.states` entry (the same mechanism `shoot --state` uses) and `--param spawn=x,y,z` / `--param seed=7` pin what no state covers; both are echoed on stderr and in the record's `state`/`params` beside `overrides`. Pinning brightway-park's `paused` state across two runs gave identical draws (1095) and triangles (100,177), where the unpinned pair of one build differed by 9.5%.

The capped clock still cannot resolve a cost smaller than one display frame, because headless Chrome runs rAF on a 60 Hz BeginFrame and every sample snaps to 16.7 ms — one pinned grayscale run read 23.2 ms and its repeat 16.8 ms with identical draws. The default uncapped clock moves frame times onto real milliseconds (`--capped` keeps the 60 Hz clock): it launches the browser with `--disable-frame-rate-limit --disable-gpu-vsync --run-all-compositor-stages-before-draw` (the first two alone leave rAF at 17.2 ms), refuses to run when a 300 ms blank-page probe says the clock is still vsynced, and marks the record `frameClock: "uncapped"`, so never compare those ms with a capped record. On brightway-park's `paused` state the uncapped clock read 4.78, 4.92, 4.94 and 5.34 ms over four back-to-back repeats (median 4.93, ±4%); while other agents were landing PRs the same build ranged 4.78–7.29 ms, because an uncapped frame carries the machine load the capped clock rounds away. Repeat a pair before claiming a delta, and prefer pairs measured back to back: ten paired plain→grayscale runs on that scene averaged +0.1 ms with individual pairs from −1.1 to +2.2 ms, so that filter's cost is below what this timer resolves under load.


CI never boots a game, downloads a model or gates a timing. `bun run perf gate` measures every game under `games/` with a web entry, one at a time; `--games a,b` narrows a run. On the RTX 3070 at 1600x900, every game's p95 must hold 16.7 ms; other GPUs print frame times without judging them. There are no game exceptions. The gate reads each game's `perf-budget.json`, falling back to `scripts/perf-budget.json`, for GL allocation limits after the 5 s warmup. Draws are diagnostic, not a budget: `drawsFrame` is the p95 of every GL draw in a frame across all passes, including extension multi-draw calls, while the renderer's single-sample `draws` covers a different interval. An older record's `draws` cannot be compared with `drawsFrame`. The gate walks through every game at high quality with `graphics.auto=false`, and keeps each raw record in `.scratch/perf-gate/`. Establish that other apps are not using the GPU before trusting timings.

`bun run verify:fast` boot-probes the games a change reaches (a game's own files, or for an engine change one game whose imports reach it, harbor-heat first), beside the tests, with models linked from the shared asset store. The probe waits on the game itself: once the shell stamps `data-jg-phase`, it gives a late readout 300 rendered frames before calling it absent. A game that throws before mounting fails with the error; one that neither mounts nor throws fails after 5 minutes.

CPU timings are measured in `bun test`; `bun run perf timing` re-runs them with `JG_TIMING_GATE=1` when you want the ceilings judged. A test prints its timing every run and asserts a ceiling only under that flag, so a loaded machine never fails the unit suite. The gate reads the fastest sampled window and scales the budget by a machine-speed reference, so a busy or slower runner passes and only the code's own regression fails (`scripts/timing-budget.ts` documents the rule; each call site names its budget and baseline).

Use these budgets when reviewing frame metrics:

| Profile | Frame budget | Draw-call budget | Triangle budget |
| --- | ---: | ---: | ---: |
| flat | 16.6 ms | 300 | 500,000 |
| cinematic | 16.6 ms | 600 | 1,500,000 |

PRs that add authored world content must include a before/after `debug_snapshot` pair. Capture both snapshots on the same hot path and compare `frame.avgFrameMs` with `render.drawCalls` and `render.triangles` against the applicable budget above; `debug_snapshot` carries the renderer's single sample, so use `bun run perf` when the claim is about a frame's whole draw cost (`render.drawsFrame`).

1. Run the game (`bun dev`), warm it up, call `debug_perf_reset` through the agent bridge (or F2+D's Perf panel), play the hot path, then take a `debug_snapshot` — reset drops load/shader-compile stalls from the frame window; the snapshot's `why` line names the culprit.
2. Read `frame.avgSimMs` vs `frame.avgOutsideMs`: sim-heavy means game logic (wrap hot `onTick` work in `measure("name", fn)` and re-snapshot; phases rank themselves); outside-heavy means render/GPU — check `render.drawCalls`/`render.triangles` and the long-frame log.
3. Fix at the owning seam, then re-run the same sequence and report before/after `avgFrameMs` + `render` counts as the evidence pair. Draw/triangle counts are deterministic and survive slow CI hardware; raw fps there is not the player's fps.
4. In-browser, F2+D opens the same data as the Perf panel; `debug_report` returns the unabridged snapshot.
